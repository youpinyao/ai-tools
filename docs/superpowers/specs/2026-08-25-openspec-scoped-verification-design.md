# OpenSpec 范围指纹与紧凑验证账本设计

## 背景

当前验证闭环使用工作区级指纹：对 `HEAD`、索引状态以及全部未忽略文件计算摘要。
这种做法能够发现验证后的任意变化，但也会让与当前 change 无关的文档、临时文件或并行
工作失效，迫使使用者重复执行 verify。

当前 `verification.md` 模板还同时维护验证范围、需求映射、自动化验证、人工验证、
非功能验证、代码审查、执行历史、风险与回滚。多个章节表达相同检查的计划和结果，
apply 与 verify Agent 又会反复读取和重写整份文件，导致小 change 也消耗较多 token。

## 目标

- 硬门禁只保护当前 change 明确声明的代码、测试、配置和 change 制品。
- 范围内文件在验证后发生新增、删除、重命名、类型或内容变化时，旧门禁失效。
- 范围外变化只产生告警，不阻止 sync 或 archive。
- `verification.md` 保留可审计的最终检查结果、代码审查结论和剩余风险，但不重复规范、
  tasks 或原始命令输出。
- 小 change 的验证文档保持紧凑；复杂 change 仍可按需增加检查行。

## 非目标

- 自动推断文件与业务 change 的完整语义归属。
- 取消验证、代码审查或未处理 Critical / Important 的阻断规则。
- 修改 OpenSpec 官方 verify、sync 或 archive 的默认语义。
- 在 `verification.md` 中保存完整测试日志或每轮修复的逐步历史。

## 方案概览

采用“范围声明 + 范围摘要 + 内容指纹 + 紧凑账本”：

1. verify 在读取完整实现 diff 后声明本次验证范围。
2. 指纹脚本只计算范围声明命中的代码、测试、配置和当前 change 制品。
3. 门禁同时绑定基线、范围声明摘要和范围内容指纹。
4. sync/archive 重新计算这两个摘要。范围内变化阻断，范围外变化仅告警。
5. `verification.md` 使用一张统一检查表，代码审查和风险分别保留一个紧凑区块。

范围声明是门禁的信任边界。隔离 worktree 中可以从本次完整 diff 自动形成候选范围；
当前工作区可能混有其它工作，verify 必须明确记录包含与排除项，不能把“所有当前改动”
直接等同于 change 范围。

## 紧凑验证账本

模板调整为以下逻辑结构：

```markdown
## 范围
- 基线：<commit>
- 包含：<路径或路径前缀>
- 排除：无

## 检查
| 覆盖项 | 命令或步骤 | 状态 | 证据 |
|---|---|---|---|
| <requirement/scenario ID> | <真实命令或步骤> | 待执行 | |

## 代码审查
- 范围：<基线与 diff>
- 结论：待执行
- 发现：无

## 风险与回滚
- 剩余风险：无
- 回滚：不适用
```

约束如下：

- “覆盖项”引用 requirement、scenario 或 task ID，不复制其正文。
- 自动化、人工和非功能检查使用同一张表；检查类型可写入“覆盖项”。
- 同一检查重跑时更新原行，不追加一份历史表。
- 证据只记录退出码、关键摘要和日志或报告路径，不粘贴完整输出。
- 中间修复轮次压缩为最终证据中的一句摘要；未解决失败必须保留。
- 没有相关内容时使用“无”或“不适用”，不创建空的可选章节。
- 代码审查只有一个权威状态，不再在其它表格重复维护。
- 门禁机器块由工具维护，不由 Agent 复制解释性正文。

模板目标为不超过 30 行主体内容；典型小 change 生成的验证账本（不计工具维护的机器块）
不超过 40 行。该目标是维护预算，不是运行时硬校验，复杂 change 可以通过增加检查行
合理超出。

## 范围声明

`verification.md` 保留唯一的机器可读范围块：

```text
<!-- AI_TOOLS_VERIFICATION_SCOPE_V2_START -->
baseline: <完整 commit SHA>
include:
- <仓库相对路径或以 / 结尾的目录前缀>
exclude:
- <仓库相对路径或以 / 结尾的目录前缀；无则写 none>
<!-- AI_TOOLS_VERIFICATION_SCOPE_V2_END -->
```

路径规则：

- 所有路径使用仓库根目录下的 POSIX 相对路径，不允许绝对路径或 `..`。
- 文件路径精确匹配；以 `/` 结尾的路径匹配该目录下所有后代。
- `exclude` 只能缩小 `include`，不能声明范围外路径。
- 当前 change 根目录始终加入 `include`。
- `verification.md` 的结果块从内容指纹中排除，其他正文和范围块参与计算。
- 主规范只有在本次 change 明确直接修改它时才加入范围；正常 sync 产生的 main spec
  更新不使实现验证失效，sync 自身仍须执行官方规范校验。

verify 应根据已审查的完整 diff 生成候选范围，并显式检查：

1. 每个实现、测试、配置和 change 制品路径都被 `include` 命中。
2. `exclude` 中没有本次 change 依赖的文件。
3. 对无法确定归属的路径先报告歧义，不静默排除。

隔离 worktree 允许以完整 change diff 生成候选范围。当前工作区模式下，候选范围必须
区分既有无关改动；无法可靠区分时停止并要求用户选择，不回退到全工作区指纹。

## 指纹算法

指纹脚本输出结构化结果：

```text
scope_digest=<sha256>
content_digest=<sha256>
outside_changes=<数量>
```

### 范围摘要

`scope_digest` 对规范化后的以下内容计算 SHA-256：

- 算法版本 `v2`；
- 完整 baseline commit SHA；
- 排序、去重后的 `include`；
- 排序、去重后的 `exclude`。

任何范围规则变化都使旧门禁失效。

### 内容指纹

`content_digest` 对每个范围内路径按字节序排序后计算，输入至少包含：

- 仓库相对路径；
- 文件类型和可执行位；
- 文件内容，或删除标记；
- 符号链接目标；
- 范围内 submodule 的 gitlink commit。

计算使用工作树当前字节，因此覆盖 tracked、staged、unstaged 和 untracked 文件。
范围内 submodule 若存在未提交变化，直接返回阻塞，不把脏状态压缩成可通过摘要。

为发现新增文件，目录前缀必须在每次计算时重新枚举其后代，不能只复用 verify 时的
文件清单。枚举对象限于 tracked 文件和未被 Git 忽略的 untracked 文件，避免把依赖缓存
或构建缓存纳入摘要。对精确文件路径，即使文件不存在也加入删除标记。

### 范围外变化

脚本比较 baseline 与当前 Git 状态，列出未被范围声明命中的变化：

- 范围外变化不改变 `content_digest`，也不单独阻止 sync/archive。
- 命令输出告警路径摘要；数量过多时只显示前若干项和总数。
- 若 Agent 判断其中某项实际属于当前 change，必须扩展范围并重新 verify，不能忽略告警。

## 门禁结果

验证结果块升级为 V2，至少记录：

```text
<!-- AI_TOOLS_VERIFICATION_RESULT_V2_START -->
- 状态：通过
- 阻塞项：无
- 范围摘要：<scope_digest>
- 内容指纹：<content_digest>
<!-- AI_TOOLS_VERIFICATION_RESULT_V2_END -->
```

sync/archive 仅在以下条件全部满足时继续：

1. 恰好存在一个 V2 范围块和一个 V2 结果块。
2. 状态为“通过”，阻塞项为“无”。
3. 当前 `scope_digest` 与记录值一致。
4. 当前 `content_digest` 与记录值一致。
5. 代码审查没有未处理 Critical 或 Important。

范围外告警必须向用户汇报，但不改变以上判定。范围内摘要不匹配时必须重新 verify，
不得通过用户确认直接绕过。

## 数据流

### Verify

1. 确定 baseline，并读取本次 change 的完整 diff。
2. 生成并审查范围声明。
3. 执行统一检查表中的适用检查。
4. 针对范围内完整 diff 执行代码审查。
5. 安全修复后更新原检查行，并重新执行受影响检查和完整代码审查。
6. 写入最终风险、V2 范围块和结果块。
7. 计算两类摘要，回填后再次计算确认稳定。

### Sync / Archive

1. 解析唯一 V2 范围块和结果块。
2. 重新计算范围摘要和内容指纹。
3. 摘要不匹配则阻止流转并指出变化路径。
4. 只有范围外变化时显示告警并继续官方主体。
5. sync 后直接 archive 时，main spec 的正常同步变化不要求重新执行实现验证；官方规范
   校验失败仍按官方流程阻止或报告。

## 失败处理

- 范围块格式错误、路径越界或 baseline 不存在：阻断，并要求修复范围声明。
- 范围目录无法读取：阻断，不使用旧摘要。
- 范围内文件在验证后变化：阻断并列出变化路径，重新 verify。
- 只有范围外文件变化：告警但不阻断。
- 无法判断某项是否属于 change：停止并让用户确认范围。
- 检查失败或代码审查有未处理 Critical / Important：写“阻塞”结果，不生成有效指纹。

## 迁移

- 新建 change 直接使用 V2 模板和算法。
- 已有 V1 通过门禁不自动转换，因为旧结果没有可信的范围声明。
- 已有 active change 在下一次 sync/archive 前执行一次 verify，生成 V2 范围与结果块。
- V2 写入时删除旧 V1 结果块，避免双重权威状态。
- 接入文档、指纹脚本和 apply/verify/sync/archive 注入规则必须在同一次升级中发布，避免
  新旧算法混用。

## 验收标准

- 小 change 的模板主体不超过 30 行，默认生成内容不重复 requirement 正文或原始日志。
- 同一检查复验后仍只有一行权威结果。
- 修改范围内 tracked、staged、unstaged 或 untracked 文件会导致内容指纹不匹配。
- 在范围目录内新增、删除或重命名文件会导致内容指纹不匹配。
- 只修改范围外文件不会阻止 sync/archive，但会产生可见告警。
- 修改范围声明会导致范围摘要不匹配。
- 修改 `verification.md` 的证据或风险会导致内容指纹不匹配；只更新结果块本身不会递归
  改变指纹。
- 正常 sync 更新未纳入范围的 main spec 后，可以继续 archive，无需重复实现验证。
- V1 active change 在未重新 verify 生成 V2 前不能使用新门禁流转。

## 风险与权衡

- **范围声明遗漏真实依赖** → verify 必须从完整 diff 生成候选范围并审查范围外告警；
  无法判断时要求用户确认。
- **目录前缀过宽导致门禁再次敏感** → 优先使用最小稳定目录或精确文件，避免仓库根前缀。
- **精确文件过多增加 token** → 对边界清晰的模块使用目录前缀；机器块不重复文件证据。
- **范围外恶意变化不被阻断** → 这是从全工作区完整性切换为 change 完整性的明确取舍；
  CI 和分支保护仍负责仓库级完整性。
- **V1 迁移需要一次复验** → 不猜测旧验证范围，以一次性成本换取 V2 信任边界明确。
