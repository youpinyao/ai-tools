# AI-SDD 团队工作流

## 目标

这套流程的目标不是提高 AI 代码占比，而是降低需求误解、人工 Review、测试补漏和上线返工成本。

团队以 OpenSpec 作为需求与实现之间的可追溯契约，以可重复执行的验证证据作为完成标准。

## 工作流

```text
proposal
  → backend / frontend specs
  → design
  → tasks
  → verification plan
  → apply
  → implementation evidence
  → independent verify
  → archive
```

各机制的职责：

- `openspec/config.yaml`：约束所有变更的生成质量。
- `evidence-driven/schema.yaml`：定义产物顺序和依赖关系。
- `/opsx:apply`：实施任务并记录实际验证证据，但不能批准自己的实现。
- `/opsx:verify`：由独立 Agent 在新会话中验证并填写最终结论。
- `/opsx:archive`：执行硬门禁，验证未通过时禁止归档。
- 本文档：解释风险分级、协作方式和团队治理要求。

## 前后端独立 Spec

前后端行为必须放在独立 capability spec 中：

```text
specs/<domain>-backend/spec.md
specs/<domain>-frontend/spec.md
```

后端 spec 负责：

- 服务端业务行为
- API 请求、响应和错误语义
- 权限、幂等、并发和事务
- 数据结构、迁移和兼容性

前端 spec 负责：

- 用户行为和交互结果
- 加载、空数据、错误、重试和权限状态
- 前端校验和运行时异常
- 对后端契约的消费方式

前后端不得复制两份独立维护的完整契约。双方通过以下至少一种稳定标识建立关联：

- API 路径和 HTTP 方法
- OpenAPI `operationId`
- Schema 名称
- 明确的契约版本

后端通常是接口契约的所有者，前端 spec 引用契约并定义消费行为。

## 风险分级

### Low

判断条件：

- 影响范围局限于单个模块。
- 不修改公共 API、权限边界或持久化结构。
- 回滚简单，不影响关键业务链路。

要求：

- 明确需求和验收场景。
- 完成定向测试、编译和静态检查。
- 独立 Agent 验证后才能归档。

### Medium

任一条件成立：

- 跨多个模块。
- 修改前后端契约，但保持向后兼容。
- 包含可回滚的数据迁移。
- 需要功能开关、灰度或跨团队协调。

附加要求：

- 明确设计决策和备选方案。
- 完成契约测试、集成测试和回滚分析。
- 设计或发布方案需指定责任人审批。
- 剩余风险必须被明确接受。

### High

任一条件成立：

- 破坏性 API 或契约变更。
- 不可逆或高数据量迁移。
- 涉及认证、授权、资金、隐私或敏感数据。
- 影响核心性能、可用性或多个外部系统。

附加要求：

- 实现前必须完成人工设计审批。
- 必须包含安全、容量、迁移和回滚验证。
- 必须定义灰度范围、观察指标、失败阈值和回滚责任人。
- 未经人工接受剩余风险不得归档。

不确定风险等级时，采用更高一级。

## 任务与变更粒度

任务按可观察行为拆分，而不是按技术层拆分。

不推荐：

```text
实现 Controller
实现 Service
实现页面
补充测试
```

推荐：

```text
建立失败测试
实现一个最小用户行为
执行定向验证
形成可独立 Review 的增量
```

后端和前端分别关联各自 spec。契约变化时增加独立的联调任务，同时引用双方的 Requirement 和 Scenario。

一个任务只有在测试和验证证据完成后才能勾选。任务全部完成不代表可以归档。

## 独立验证

实现 Agent 负责：

- 执行 `verification.md` 中适用的检查。
- 记录真实命令、结果和证据。
- 标记失败、跳过项和剩余风险。
- 不填写“独立验证结论”。

独立验证 Agent 负责：

- 必须在没有参与实现的新会话中运行 `/opsx:verify <change-name>`。
- 重新执行构建、静态或类型检查以及定向测试。
- 检查任务完整性、需求正确性和设计一致性。
- 将结论写回 `verification.md`。

归档只接受：

```text
验证结论：通过
```

以下情况必须阻塞：

- Artifact 或任务未完成。
- 适用检查仍为“待执行”或“失败”。
- 存在未解决的 CRITICAL 问题。
- Medium/High 风险变更缺少要求的审批。
- 剩余风险未被明确记录和接受。

## 项目接入清单

本仓库提供团队级通用基线。每个业务项目接入时，项目负责人必须根据实际仓库补充以下信息，不得直接复制示例值或让 AI 自行猜测。

### 技术栈与构建

- Java、Spring Boot、Node.js、TypeScript 和 Vue 的实际版本。
- 后端使用 Maven 或 Gradle，以及 Wrapper 的标准入口。
- 前端使用 npm、pnpm 或 yarn，以及锁文件要求。
- 模块目录、源码目录、测试目录和生成代码目录。
- 本地开发、构建、格式化、静态分析和类型检查的真实命令。

### 测试与 CI 门禁

- 后端单元、集成、契约和端到端测试框架及执行命令。
- 前端单元、组件和端到端测试框架及执行命令。
- CI 必须执行的检查、超时时间和允许跳过的条件。
- 测试覆盖率要求及适用范围。
- 哪些失败属于归档或合并的硬阻塞项。

### API 与前后端契约

- OpenAPI 或其他接口契约文件的事实来源位置。
- API 路径、`operationId`、Schema 和版本命名规范。
- TypeScript Client 和类型的生成命令及输出目录。
- 契约兼容性检查命令。
- 破坏性变更的版本升级、迁移和通知策略。

### 数据与迁移

- 数据库类型、迁移工具和迁移文件目录。
- 向前兼容、向后兼容和混合版本运行期限。
- 数据回填、锁、批处理和容量限制。
- 回滚条件、回滚命令以及不可逆操作的审批要求。

### 安全与敏感数据

- 认证、授权和权限边界。
- 敏感数据、个人信息、密钥和令牌的分类规则。
- 日志脱敏、数据保留和审计要求。
- 必须进行人工安全审查的变更类型。

### 负责人和审批

- 各模块、API 契约、数据库和发布流程的负责人。
- Medium 风险变更的设计或发布审批人。
- High 风险变更的设计、安全、数据和业务审批人。
- 剩余风险的接受人以及接受记录位置。

### 发布与可观测性

- 部署环境、发布顺序、功能开关和灰度策略。
- 必须观察的日志、指标、链路、告警和业务指标。
- 发布成功标准、观察期限和失败阈值。
- 回滚责任人、触发条件和操作步骤。

### 写入位置

- 跨产物且长期稳定的信息写入 `openspec/config.yaml` 的 `context`。
- Proposal、Specs、Design、Tasks、Verification 的专属约束写入对应 `rules`。
- 详细架构、命令说明和运维手册保留在业务仓库文档中，并在配置中引用其路径。
- CI、权限和审批系统必须承担真正的强制执行；OpenSpec 配置只负责指导 Artifact 生成。
- 配置中不得保留 `<placeholder>`、`TBD` 或未经确认的示例命令。

完成清单后，应执行：

```bash
openspec schema validate evidence-driven
openspec status
```

确认配置可以加载，并通过一次 Low 风险示例变更验证 Proposal、前后端 Spec、Tasks、Verification 和 Archive 门禁。

## 团队落地

先选择一个团队试点 2 至 4 周，不要立即覆盖所有项目。

每周回顾：

- PR 首次通过率。
- Review 往返次数。
- 人工 Review 时长。
- AI 代码被人工重写的比例。
- 验收场景的自动化覆盖率。
- 上线逃逸缺陷数量。

不要以代码行数、AI 代码占比或单纯编码时间作为主要提效指标。

当流程成本明显高于变更风险时，应调整风险分级，而不是绕过验证门禁。
